# ADR-003: ScraperManager com isolamento de falhas e relatório estruturado

## Status
Aceito — implementado em 2026-10-05

## Contexto
O PRD exige que "um scraper que falhar não interrompe os demais" (docs/prd.md:585) e que "o e-mail informe quais fontes falharam durante a coleta" (:588). Isso significa que o resultado da coleta não pode ser apenas a lista de vagas — as falhas precisam chegar intactas até a etapa do e-mail, que roda vários passos depois.

## Decisão
- **`src/services/ScraperManager.ts`**: `collect(): Promise<ScrapeResult>`, onde `ScrapeResult = { jobs: RawJob[], failures: ScraperFailure[] }`. `ScraperFailure` carrega `source` e `error` (mensagem, não stack — o stack vai para o log via Logger).
- **Isolamento por try/catch dentro do loop**: cada scraper executa em iteração própria; exceção é capturada, logada com `Logger.error` (stack completo) e adicionada a `failures`. O loop nunca aborta.
- **Coleta sequencial, não paralela**: `for` com `await` simples. Volumetria esperada é baixa (poucos boards, dezenas de vagas), e a sequência simplifica logs ordenados e debugging. Se um dia a latência for problema, trocar por `Promise.allSettled` é trivial e não muda o contrato.
- **Nenhuma integração com o `JobRunner` ainda**: o stub `ScraperManager.collect` no pipeline continua como está. A montagem do pipeline real acontece quando as etapas adjacentes (Normalizer como próxima) existirem, para não acoplar o contexto a dados que ainda mudam.

## Consequências
- Positivas: regra do PRD implementada e testada; falhas estruturadas disponíveis para o futuro e-mail de resumo; scrapers executam independentes entre si.
- Negativas: `collect` retorna um resultado composto, então consumidores precisam lidar com as duas partes (vagas e falhas) — aceito, pois é exatamente o que o e-mail precisa.
- Alternativas rejeitadas: relançar a exceção após logar (violaria a regra de não interromper); acumular vagas via callback/evento (complexidade sem ganho para N pequeno).

# ADR-001: Logger, JobRunner e pipeline stub com contexto compartilhado

## Status
Aceito — implementado em 2026-10-05

## Contexto
O PRD define um pipeline sequencial com 12 etapas (docs/prd.md:150) orquestrado pelo `JobRunner`, mas nenhuma das etapas existia. Era necessário um ponto de partida que:

1. Fizesse `npm run collect` funcionar de ponta a ponta (o `package.json` já apontava `dist/core/JobRunner.js` como entrypoint).
2. Permitisse plugar as etapas reais (Normalizer, Validator, scrapers etc.) nas próximas tarefas sem redesenhar a orquestração.
3. Centralizasse o logging, já que o PRD exige que todas as exceções sejam registradas por um Logger único.

Além disso, o build quebrava: o `tsconfig.json` usava `rootDir: "."` compilando também `tests/`, gerando saída em `dist/src/core/JobRunner.js` — divergente do entrypoint `dist/core/JobRunner.js` configurado no `package.json`.

## Decisão
- **`src/utils/Logger.ts`**: classe estática com níveis `info`/`success`/`warn`/`error`, timestamp ISO e emojis no padrão do projeto (🎮 ✅ ⚠️ ❌). `error` aceita um `Error` opcional e imprime o stack trace.
- **`src/core/JobRunner.ts`**: orquestrador genérico que recebe `PipelineStep[]` e executa em ordem com **fail-fast** (primeira exceção interrompe e propaga o erro, conforme docs/prd.md:200). Um `PipelineContext` (mapa chave-valor) é criado no início de `run()` e compartilhado entre todas as etapas — é o mecanismo pelo qual etapas produzem e consomem dados (jobs normalizados, estado, vagas novas) sem acoplamento direto.
- **Contrato `PipelineStep`**: `{ name: string; run(context): Promise<void> }` — uma interface, não classe abstrata, para não impor construtor às etapas futuras.
- **`createDefaultPipeline()`**: as 12 etapas do PRD como stubs que logam "ainda não implementada" e seguem em frente. Assim o pipeline já roda completo hoje e cada tarefa futura substitui um stub por uma implementação real.
- **Entrypoint no próprio módulo**: guard `import.meta.url === pathToFileURL(process.argv[1])` para que `node dist/core/JobRunner.js` execute o pipeline sem arquivo separado.
- **Build**: `tsconfig.build.json` dedicado (`rootDir: ./src`, apenas `src/`), usado pelo script `npm run build`, sem alterar o `tsconfig.json` base (necessário com `rootDir: "."` para ts-jest e ESLint cobrirem os testes).

## Consequências
- Positivas: `npm run collect` executa o pipeline completo com stubs; etapas futuras são aditivas (substituir stub, sem tocar no JobRunner); logging padronizado desde já; entrypoint do `package.json` passa a resolver.
- Negativas: o `PipelineContext` é `unknown`-typed por chave — etapas farão casts até o pipeline inteiro ser tipado. Aceito por ora: a tipagem forte chega naturalmente quando as etapas forem implementadas e o formato dos dados estabilizar.
- Alternativas rejeitadas: classe abstrata `PipelineStep` (imporia construtor sem necessidade); injeção de dependências por construtor no JobRunner (prematuro com apenas um colaborador real hoje).

## Validação
- `npm run lint` — 0 erros
- `npx tsc --noEmit` — OK
- `npm test` — 6 suítes, 15 testes, todos passando (3 novos do JobRunner: ordem sequencial, fail-fast, contexto compartilhado)
- `npm run collect` — pipeline completo executa de ponta a ponta
